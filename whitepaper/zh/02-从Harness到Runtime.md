# 第一章 从 Harness 到 Runtime：Agent 稳定工作的真正挑战

## 1.1 Agent 走到了哪里：三个阶段

回顾 AI Agent 的发展，可以清晰地看到三个阶段。

**第一阶段：能力涌现（2023）。** GPT-4 的发布打开了 Agent 的想象空间。AutoGPT、BabyAGI、MetaGPT 等项目证明了一件事：大模型不只能回答问题，还能规划任务、调用工具、执行多步操作。这个阶段的关键词是"惊艳"——人们兴奋于 Agent 能做到什么，却很少有人认真讨论它做得对不对、稳不稳定、出了问题怎么办。

**第二阶段：接入世界（2024–2025）。** 兴奋消退后，行业开始解决一个实际问题：怎么把模型接到真实的工具和环境上。这就是 **Harness Engineering** 与 **Context Engineering** 的时代。MCP（Model Context Protocol）成为连接模型与外部系统的开源标准；LangChain、CrewAI、LangGraph 等框架解决了工具调用、多 Agent 编排、上下文管理等问题。这个阶段的核心成果，是让 Agent "能动起来"——能查数据库、能调 API、能读写文件。

**第三阶段：稳定运行（2026–）。** 这正是我们现在所处的位置。行业逐渐意识到：让 Agent 动起来只是第一步，让它**长时间、稳定、可恢复、可审计、可协作**地运行，才是真正的挑战。

2026 年的信号已经非常明确：OpenAI 最新的 Agents SDK 开始强调原生 sandbox、snapshotting and rehydration（快照与状态恢复）、面向长时任务的持久执行；Anthropic 把 long-running agents、managed agents、agent evals 作为核心方向；Google 在推 A2A（agent-to-agent）协作协议。行业重心正在从"让 Agent 动起来"，转向"让 Agent 在世界里稳定工作"。

## 1.2 从 Harness 到 Runtime：核心问题是什么

用一个准确的概括来说：**Harness 解决的是"把模型接入世界"，Runtime 解决的是"让它在世界里稳定工作"。** Harness 不是终点，它只是第一层。

当我们真正把 Agent 推向生产，关注点会发生根本转移——从"它能不能调用这个工具"，变成"它跑了三个小时、改了几十张表、调了十几个 API 之后，我还能不能相信它、还能不能在它出错时把一切恢复原状"。这就是 **Agent Runtime Engineering** 要回答的问题。

## 1.3 Agent Runtime 的四个核心问题

Agent Runtime 要解决的核心问题，可以归纳为四个。

### 1. 状态管理与持久执行

真正有价值的 Agent 任务，不是一次 prompt 里完成的短任务，而是跨文件、跨工具、跨多轮上下文持续推进的长任务。这类任务需要状态的持久化、失败的恢复、任务的续跑和检查点的提交。OpenAI 已经把 long-horizon tasks 和 snapshotting 写进了路线图，Anthropic 则把"跨多个上下文窗口做增量推进"当成核心挑战。

> **本质需求：Agent 需要一个能持久化状态、支持快照和恢复的数据层。**

### 2. 可观测、可评估、可审计

Agent 的难点不在首轮 Demo，而在上线之后——怎么知道它哪一步出了问题、为什么会漂移、什么时候该拦截、什么时候该回滚。评估不再只是"最后答对没有"，而是要看整个执行链路是否可观测、可诊断、可审计。

> **本质需求：Agent 的每一步操作都需要可追溯，执行结果需要可对比、可回滚。**

### 3. 协议与协作

MCP 解决了 Agent 如何标准化地接入工具和数据，A2A 解决了 Agent 之间如何发现彼此、描述能力、发起协作。系统一旦复杂，协议层的重要性就会凸显——它决定了可组合性、迁移成本和生态扩展速度。但 Agent 之间要真正协同完成一件事，仅有消息传递还不够，还需要**数据层面的隔离与合并**。

> **本质需求：Agent 需要一个统一的数据基座，让不同 Agent 能安全地共享和协作操作数据。**

### 4. 记忆与状态治理

记忆当然重要，但它正在从"单独的热点"变成 Runtime 的一个子系统。记忆真正起作用，不只是"存下来了"，而是能不能在合适的时机被检索、被注入、被验证，并且和当前工作状态保持一致。OpenAI 现在讲 skills、compaction、long-running work，本质上已经不是狭义的 memory 了，而是在讲如何让 Agent 在长任务中维持有效的工作状态。

> **本质需求：记忆需要和业务数据共享同一套状态管理和版本控制基础设施。**

## 1.4 四个问题，指向同一个缺口：版本控制

如果把这四个需求抽象一层，会发现它们指向同一个尚未被充分建设的基础设施层：

| Runtime 需求 | 所需的底层能力 |
|---|---|
| 状态管理与持久执行 | **快照** 和 **恢复** |
| 可观测、可审计 | **追溯** 和 **比较** |
| 协作 | **隔离** 和 **合并** |
| 记忆治理 | **版本化** 和 **冲突检测** |

**快照、恢复、追溯、比较、隔离、合并、版本化、冲突检测——这正是版本控制系统的全部能力。**

Agent Runtime 需要的不是一个新发明，而是一套在软件工程中已经被验证了三十年的范式——**版本控制**——在数据层面的原生实现。代码有 Git，Agent 的数据和状态也需要一个 Git。

## 1.5 为什么只能在数据库内核中实现

但这个"数据的 Git"，远比代码的 Git 苛刻。它必须能处理 **TB 级的结构化数据**，必须提供 **行级别的 diff** 和 **语义级的 merge**，必须保证 **事务的原子性**——任何把数据完整导出再比较、或在应用层模拟版本的做法，在生产规模下都会瞬间崩溃。

**这只能在数据库内核中实现。**

只有当不可变存储、多版本并发控制、存算分离等能力从内核层面被原生设计出来，"零拷贝的分支""增量的 diff""原子的 merge"才可能在 TB 级数据上以亚秒到秒级的代价完成。这也正是为什么——大量"在向量库外面包一层 RAG""在应用层维护一份记忆"的方案，永远无法真正承载 Agent Runtime：它们缺的不是功能，而是内核级的版本控制地基。

## 1.6 风口与鸿沟

这一判断，也解释了当下 Agent 市场"冰火两重天"的根本原因。

一面是空前的热度。Gartner 预测，到 **2026 年底，40% 的企业应用将内置任务型 AI Agent**（2025 年还不到 5%）；2026 年 Q1 新发布或更新的企业应用中，已有 **80%** 至少内置一个 Agent。全球 AI Agent 市场 2026 年预计达百亿美元量级，年复合增长率超过 40%。

另一面是冷峻的现实。Gartner 同时警告：**到 2027 年，超过 40% 的 Agentic AI 项目将被取消**，主因是成本失控、商业价值不清晰、风险与治理无法落地。当前真正部署了 Agent 的组织仅约 **17%**，而横在多数企业面前最大的拦路虎，正是——**Agent 跑得起来，却"稳"不下来、"信"不过去。**

热度与落地之间这道鸿沟的根因，不在模型，而在 **Agent Runtime 的数据基础设施缺位**：没有可持久化、可恢复的状态层，长任务一断就前功尽弃；没有行级可追溯的审计，没人敢让它碰核心业务；没有隔离与合并，多 Agent 协作寸步难行；没有版本化的记忆，它在长期交互中不断自相矛盾、放大幻觉。

要跨越这道鸿沟，企业需要的正是一套**版本控制原生的数据与记忆底座**。接下来的两章，我们将讲述矩阵起源如何用五年时间，在数据库内核中把这套底座一寸一寸地建造出来。
