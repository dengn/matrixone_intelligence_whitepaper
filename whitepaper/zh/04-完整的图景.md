# 第三章 完整的图景：版本控制原生的 Agent 数据基础设施

第一章提出了 Agent Runtime 的四个核心需求，并论证了它们共同指向一个缺口——数据库内核级的版本控制。第二章讲述了矩阵起源如何用五年时间把这块地基建造出来。本章，我们把所有组件放在一起，呈现一张完整的技术全景，并逐一回答：**Agent 需要什么，我们有什么。**

## 3.1 技术全景

矩阵起源的 AI 基础设施全景，自下而上分为四层：

```
┌──────────────────────────────────────────────────────────────┐
│  应用层  Application                                          │
│    Branch as Sandbox（Agent 的安全执行环境）                  │
│    Git for Agent（Agent 的自我进化）                          │
├──────────────────────────────────────────────────────────────┤
│  双支柱  Two Pillars                                          │
│    MOI 数据平台（Agent 的"数据库"：NL2SQL/语义层/多模态/检索）  │
│    Memoria 记忆层（Agent 的"内存"：版本化记忆/分支/合并）       │
├──────────────────────────────────────────────────────────────┤
│  核心能力层  Version Control Primitives                       │
│    snapshot · clone · diff · merge · revert                  │
│    （TB 级数据上亚秒级 clone、秒级 diff/merge）                 │
├──────────────────────────────────────────────────────────────┤
│  底层  MatrixOne 数据库内核                                    │
│    不可变存储 · MVCC · LSM 树 · 存算分离                       │
└──────────────────────────────────────────────────────────────┘
```

> 图 3-1 矩阵起源 AI 基础设施技术全景（示意，正式架构图待设计输出）

- **底层：MatrixOne 数据库内核。** 提供不可变存储、MVCC、LSM 树、存算分离。这是一切的地基。
- **核心能力层：版本控制原语。** snapshot、clone、diff、merge、revert，利用内核架构特性原生实现，在 TB 级数据上实现亚秒级的 clone 与秒级的 diff/merge。
- **双支柱：** 数据平台 **MOI**（Agent 认知世界的接口）+ 记忆层 **Memoria**（Agent 积累经验的机制）。
- **应用层：** **Branch as Sandbox**（Agent 的安全执行环境）与 **Git for Agent**（Agent 的自我进化）。

接下来，我们把 Agent Runtime 的四个核心需求，逐一与这套基础设施对应起来。

## 3.2 需求一：状态管理与持久执行 → 版本控制 + 数据平台

Agent 的长时任务需要检查点和恢复能力。MatrixOne 的 **snapshot 就是天然的检查点**——记录任务在任意时间点的完整状态。任务失败？从上一个 snapshot 恢复。任务需要续跑？从最近的检查点继续。这正是 OpenAI 所说的 snapshotting and rehydration，只不过我们在数据层把它做成了内核能力。

但状态管理不只是"保存和恢复"。Agent 在长时任务中还需要持续地查询和操作业务数据。**MOI 数据平台**提供了这个能力——Agent 可以用自然语言查询实时数据，理解数据之间的关系和趋势。而数据平台本身的数据受版本控制保护，Agent 在任务过程中对数据的每一次操作，都是可追溯、可恢复的。

## 3.3 需求二：可观测、可评估、可审计 → diff + 数据平台

这是 trust 最核心的基础。

MatrixOne 的 `SNAPSHOT DIFF` 让 Agent 的每一次操作都变成**可精确量化的变更**——它修改了哪些行、每一列从什么值变成了什么值。这不是模糊的日志，而是**行级别精度的、可用 SQL 查询和分析的结构化审计**。

**MOI 数据平台**则让审计结果变得可理解——审查者可以用自然语言提问："这个 Agent 今天修改了哪些客户的信用等级？修改前后的分布有什么变化？"数据平台会把这些问题转化为对 diff 结果的精确查询。

当 Agent 的每一个行动都是**可看到、可理解、可追溯**的，trust 才有了客观基础。

## 3.4 需求三：协作 → clone + merge + 记忆层

多个 Agent 协作同一个任务时，需要的不只是消息传递协议（如 A2A），还需要**数据层面的隔离与合并**。

MatrixOne 的 **clone** 让每个 Agent 在自己的数据分支上工作——互不干扰，共享底层存储，创建成本几乎为零；**merge** 让多个 Agent 的工作成果安全地合并到一起——自动识别冲突，原子性提交。

**Memoria 记忆层**则让 Agent 之间的"知识"也可以协作——每个 Agent 在自己的记忆分支上积累经验，再通过 merge 将各自学到的知识合并到共享记忆；系统自动识别知识冲突（两个 Agent 对同一事实的矛盾认知），交由人类或上级 Agent 仲裁。

## 3.5 需求四：记忆与状态治理 → Memoria + 版本控制

正如行业趋势所揭示的，记忆正从"单独的热点"变成 Runtime 的一个子系统。记忆真正起作用，不只是"存下来了"，而是能否在合适的时机被检索、被注入、被验证，并和当前工作状态保持一致。Memoria 的版本控制能力，正是回答这个问题的：

- **记忆的检索**：基于 MatrixOne 的全文检索与向量检索能力，精确找到与当前任务相关的历史记忆；
- **记忆的注入**：通过语义层理解记忆与当前业务数据的关系，在合适的时机将相关记忆注入上下文；
- **记忆的验证**：通过 diff 对比记忆的变化，检测是否有矛盾或过时的记忆需要更新；
- **记忆与状态的一致性**：记忆和业务数据在同一个事务框架中被管理，状态始终一致。

## 3.6 所有组件共享同一套版本控制基础设施

这是整套架构最关键、也最难被竞品复制的特性：**业务数据、Agent 记忆、执行状态，在同一个事务框架下被管理。**

当 Agent A 和 Agent B 的工作要合并时，它们各自修改的业务数据和各自积累的记忆，在**同一个事务**中被整合——要么全部成功，要么全部回滚。记忆不会更新成功而数据回滚，也不会数据提交而记忆丢失。**这种一致性，是割裂的系统（数据库 + 外挂向量库 + 独立记忆服务）从根本上无法提供的。**

这不是几个独立系统的拼凑，而是从内核到应用层一以贯之的架构。

## 3.7 应用层：Branch as Sandbox 与 Git for Agent

在版本控制原语与双支柱之上，我们把这套基础设施推向了两个面向 Agent Runtime 的应用形态。

### Branch as Sandbox：Agent 的安全执行环境

让每一个 Agent 任务都跑在一个**零拷贝创建的隔离分支**里：

- **隔离**：利用 clone 为每个任务建立沙箱，Agent 的所有操作都发生在分支上，错误不会扩散到生产环境，而创建沙箱的成本几乎为零；
- **审查**：任务完成后，用 diff 生成一份**行级变更报告**——改了哪些行、改前改后的值是什么——以"Pull Request"的形式呈现给人类审查；
- **发布**：人类确认后，用 merge 原子性地把变更发布到主线；发现问题，则直接丢弃分支，零成本回退。

这把软件工程里"分支开发—代码评审—合并发布"的成熟范式，原封不动地搬到了 Agent 操作数据的世界。Agent 第一次可以"安全地试错"。

### Git for Agent：Agent 的自我进化

把版本控制思想推向极致：不仅版本化 Agent 操作的**数据**和积累的**记忆**，还版本化 **Agent 自身的行为策略**。每一次策略调整都是一次提交，每一次效果对比都是一次 diff——用数据驱动 Agent 的持续优化，让 Agent 像一套被持续迭代的软件一样自我进化。
